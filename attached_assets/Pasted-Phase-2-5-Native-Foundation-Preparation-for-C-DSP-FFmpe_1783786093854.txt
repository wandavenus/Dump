Phase 2.5 — Native Foundation (Preparation for C++ DSP & FFmpeg)

Objective

Do NOT implement C++ DSP.

Do NOT integrate FFmpeg.

This phase is only to prepare a clean, scalable native architecture that future native modules can plug into without requiring another large refactor.

The playback engine remains Media3 only.

---

Architecture Goal

Target architecture:

Flutter UI

↓

AudioService

↓

PlaybackManager

├── Media3PlaybackBridge

├── NativeDspBridge (stub)

└── FfmpegDecoderBridge (stub)

Only Media3 is active.

The native bridges are placeholders for future implementation.

---

1. Create Native Module Foundation

Create a dedicated native module layer.

Suggested structure:

lib/services/native/

lib/services/native/bridges/

lib/services/native/contracts/

lib/services/native/models/

The structure should be modular and prepared for future expansion.

---

2. Create NativeModule Contract

Create a lightweight contract for future native modules.

Responsibilities:

- initialization
- disposal
- availability check
- capability query

Do not include DSP-specific or FFmpeg-specific APIs yet.

Keep the interface generic.

---

3. Create NativeDspBridge (Stub)

Create a bridge class only.

Do NOT implement DSP.

It should:

- compile successfully
- expose initialization lifecycle
- expose availability status
- expose placeholder capability query
- expose clean extension points

No DSP processing should exist yet.

---

4. Create FfmpegDecoderBridge (Stub)

Create a bridge class only.

Do NOT bundle FFmpeg.

Do NOT add native binaries.

Prepare only:

- lifecycle
- capability query
- decoder availability
- future decoder registration

No decoding implementation yet.

---

5. JNI / FFI Preparation

Prepare the project for future native integration.

If JNI or Dart FFI infrastructure is required:

- create minimal project structure
- keep it compilable
- avoid placeholder code that generates warnings

Do not add native DSP code.

Do not add FFmpeg.

Only prepare the bridge.

---

6. PlaybackManager Integration

PlaybackManager should become the single entry point.

Rules:

- UI never accesses native bridges directly.
- AudioService never accesses native bridges directly.
- Future services communicate only through PlaybackManager.

PlaybackManager should own:

- Media3 bridge
- Native DSP bridge
- FFmpeg bridge

Only Media3 should currently be active.

---

7. Future Extension Points

Design extension points for future modules such as:

- Native DSP
- FFmpeg Decoder
- FFT Analyzer
- Audio Visualizer
- Loudness Analyzer
- ReplayGain
- Resampler

The architecture must allow adding these without changing existing playback flow.

---

8. Documentation

Create architecture documentation explaining:

- responsibilities of every bridge
- ownership of PlaybackManager
- lifecycle of native modules
- future integration strategy

---

9. Validation

Verify:

- playback still works
- queue still works
- MediaSession still works
- notification still works
- Bluetooth controls still work
- Android Auto integration (if present) still works
- crossfade still works
- gapless still works
- preload still works
- artwork still works
- no performance regression
- no analyzer warnings
