# Production Audit — ReplayGain / Audio Normalize / Loudness Normalization Pipeline

**Scope:** Full signal path from Flutter UI down to native DSP (`.c`/`.cpp`) and Android/Media3 integration.
**Method:** Direct reading of every processor's source (not paraphrase), cross-checked against BS.1770-4, EBU R128, ReplayGain 2.0, RFC 7845 (Opus), and Media3 1.10.1 behavior.
**Constraint honored:** audit only — no code was modified.

---

## 1. Signal-Path Architecture

Real pipeline (`native_audio_runtime/lib/src/dsp_pipeline_io.dart`), one shared native C singleton, in ExoPlayer's `AudioProcessor` chain via `NativeDspAudioProcessor.kt`:

```
ExoPlayer decoder (float32 PCM)
  → slot 0  dsp.gain            (gain_processor.c)          — master volume/pre-gain
  → slot 1  dsp.replaygain      (replaygain_processor.c)    — tag-based track/album gain
  → slot 2  dsp.loudness        (loudness_processor.c)      — real-time EBU R128 auto-normalizer
  → slot 3  dsp.peq             (peq_processor.c)           — 32-band parametric EQ
  → slot 4  dsp.compressor      (comp_processor.c)          — soft-knee dynamics
  → slot 5  dsp.crossfeed       (crossfeed_processor.c)     — headphone crossfeed
  → slot 6  dsp.limiter         (limiter_processor.c)       — look-ahead brickwall limiter
  → slot 7  dsp.soft_clipper                                — final tanh safety clip
  → StereoWideningAudioProcessor → SilenceSkipping → Sonic → AudioTrack
```

**Naming clarification (important, not a bug):** the user-facing Settings label **"Audio Normalize"** (`lib/pages/settings_page/audio.dart`, `_ReplayGainSection`) is the UI name for the **ReplayGain** feature (slot 1). It is *not* a third, distinct DSP stage. The pipeline has exactly two normalization-related native slots: ReplayGain (tag-driven, static per track) and Loudness Normalization (real-time, adaptive). Anyone reading the settings screen without reading the code could reasonably believe there are three sequential normalization stages; there are two.

Engine core (`dsp_pipeline.c`): mutex-guarded registration only; the hot `process()` path is 100% lock-free/atomics-only, iterates registered slots **in order**, and **stops the entire chain on the first non-OK return code**. There is a zero-copy path (`nar_dsp_pipeline_process_raw`) used directly from the Kotlin `AudioProcessor`, and a separate boxed path for tests/other callers. Max 16 slots, duplicate-id registration rejected.

## 2. ReplayGain / Loudness-Normalization Interaction

- Not mutually exclusive at the native level — nothing in `dsp_pipeline.c` stops both slot 1 and slot 2 from being simultaneously enabled.
- Mutual exclusion is enforced one layer up, in Dart, `AudioService._applyReplayGain()` (`lib/services/audio_service/service.dart`): when `loudnessNormEnabled.value` is true, tag-based RG gain resolution/application is skipped; only the user's manual preamp is still forwarded through the RG slot. This is a deliberate, correctly implemented design decision to avoid double renormalization/oscillation between a static tag gain and an adaptive real-time normalizer.
- `AudioEffectsService.setLoudnessNormEnabled()` also disables the **system** `LoudnessEnhancer` (Android platform effect) when native LN turns on. This interlock is **one-directional only**: turning the system `LoudnessEnhancer` on later does not disable native LN. This is a real, still-open (if minor) gap — a user can end up with both a system-level loudness enhancer and the native EBU R128 normalizer active at once if they toggle the system effect after enabling native LN, defeating the purpose of the interlock.
- `LoudnessSourceResolver` (Off/Track/Album/Auto) looks correct; the "same album" heuristic in Auto mode (albumId match, else normalized artist+album string match) can misclassify various-artists compilations as different albums per track, silently falling back to Track mode. Minor, not a correctness bug against spec.

## 3. BS.1770-4 / EBU R128 Compliance

**Offline scanner** (`ebur128_analyzer.cpp`, via libebur128): uses `EBUR128_MODE_I | LRA | TRUE_PEAK | SAMPLE_PEAK | HISTOGRAM`, correct `ebur128_loudness_global_multiple()` for album-gain computation (proper multi-track integrated-loudness combination per spec, not an average of per-track LUFS values — this is the correct approach). Fully spec-compliant; this is the trustworthy "ground truth" path used when scanning/writing tags.

**Real-time normalizer** (`loudness_processor.c`): implements the actual BS.1770-4 Annex 1 K-weighting biquad derivation (not an RBJ approximation) and the correct per-channel power weighting table (LFE=0, surround channels +1.5 dB) for 1–8 channels. However, it explicitly and knowingly deviates from the spec's two-pass offline gating algorithm: it uses a **causal, single-pass approximation** — a 4×100 ms ring buffer forming rolling 400 ms blocks, absolute gate at −70 LUFS, relative gate at −10 LU under the running mean, then asymmetric one-pole smoothing (0.3 s attack / 3.0 s release). This is a reasonable, well-documented engineering tradeoff for real-time processing (true BS.1770 gating requires the whole track buffered, which is not possible in a streaming context) but it is **not** BS.1770-4-conformant loudness measurement in the strict sense — it will diverge from the true integrated LUFS value, especially on tracks with large early silence, sudden dynamic swings, or short duration (<3 s converges only after ~3 attack/release windows). This should be described to end users as "adaptive" rather than "precise EBU R128," which the current UI copy does not distinguish.

## 4. DSP Correctness (clipping / NaN / Inf / DC / instability / zipper)

- `loudness_processor.c`: explicit NaN/Inf guards on input, at each biquad stage (state reset to zero on non-finite detection), and on the final smoothed gain before it's applied — the most defensively written module in the pipeline.
- `comp_processor.c`, `limiter_processor.c`, `gain_processor.c`, `replaygain_processor.c`, `peq_processor.c`: **no NaN/Inf guards** at all. A single corrupted/garbage sample from a malformed decoder edge case would propagate unchecked through gain multiply, compressor `logf`/`expf` (NaN input → NaN `level_db` → NaN envelope → poisons all future envelope states, since `envelope_db = ca*envelope_db + (1-ca)*level_db` never recovers once NaN), and limiter peak/gain math (a NaN peak makes `desired_gain` NaN, which then poisons `gain_linear` permanently, since NaN compares false to everything and neither branch resets it). This is a real, if low-probability-in-practice, robustness gap: the loudness stage is hardened against exactly the failure mode the rest of the chain is not, and a NaN produced downstream of slot 2 (e.g. inside the compressor or limiter) is never caught before hitting `AudioTrack`.
- `dsp_pipeline.c`'s **stop-on-first-error** behavior compounds this: if any processor returns a non-OK status mid-chain, every downstream processor — including the limiter and soft-clipper, which are the safety net against clipping — is skipped entirely for that buffer. None of the current processors' `process()` implementations actually return non-OK except on `NULL` buffer/invalid argument, so this is currently a latent risk rather than an observed failure, but it means a single defensively-coded early return in any future processor addition silently disables the safety net for that buffer, with no logging.
- `limiter_processor.c`: correct look-ahead limiter — instant attack (snap down), smoothed one-pole release, clamped so it never recovers past the still-required gain. Zero risk of overshoot given the math. Sound implementation.
- `comp_processor.c`: mathematically correct quadratic soft-knee (C¹ continuous at both knee boundaries). No zipper risk — coefficients only change via the double-buffered dirty-flag swap between full audio buffers, never mid-buffer.
- `peq_processor.c`, `crossfeed_processor.c`: standard RBJ-cookbook biquads in transposed direct form II; correct, standard, no instability under normal Q/gain ranges (clamped in `biquad_filter.c`: Q∈[0.001,100], gain∈[-96,24] dB, freq clamped to (0, Nyquist·0.499)). No stability proof is done for extreme Q near 0.001 with high gain, but the clamp ranges are conservative enough that instability is very unlikely in the audible range.

## 5. Gain Computation (attack/release/hold/smoothing/oscillation)

- Time constants precomputed on the **control thread** (`nar_time_coeff`), audio thread only reads precomputed exponential coefficients — correct architecture, no per-sample `expf` calls except in the compressor (one `logf`+`expf` per **frame**, not per sample — documented tradeoff, ~2 µs/1024-frame buffer, negligible).
- **Un-guarded startup transient in `comp_processor.c`:** `_comp_init()` sets `coeff_attack = coeff_release = 0.0f` as the default (until the first `nar_comp_set_params()` call). A coefficient of 0 means the one-pole smoother in `_comp_process()` collapses to `envelope_db = level_db` — i.e., **zero smoothing, instantaneous attack and release** — while the compressor is otherwise fully active (`threshold_db = -20 dB`, `ratio = 4:1`, `bypass = 0` by default). If a caller ever fails to call `nar_comp_set_params()` before playback starts (e.g. Dart-side init ordering delay, or a future call site that forgets it), the compressor would apply an unsmoothed, sample-accurate gain-reduction contour on every frame above -20 dBFS, which is textbook zipper/pumping distortion. Per project memory, Dart is expected to force-bypass all dynamics processors until the user opts in — this note only reduces, but does not eliminate, exposure: it depends on that force-bypass actually running *before* the first audio buffer reaches this processor on every code path (cold start, service restart, crossfade-promoted secondary player — see §11).
- Limiter release clamp logic (`if (gain > desired_gain) gain = desired_gain;`) is correct and prevents any oscillation between attack/release.
- No explicit hold time anywhere in the chain (compressor/limiter go straight from attack to release with no hold segment) — acceptable for a feed-forward design, but means a signal that dips just below threshold for a single frame immediately starts releasing, which is a legitimate but audible design choice, not a spec deviation (dynamics processors are not spec-governed).

## 6. Multichannel Handling

- `loudness_processor.c`: correct BS.1770 per-channel weighting table, 1–8 ch, LFE zero-weighted, surround +1.5 dB — spec-correct.
- `comp_processor.c` / `limiter_processor.c`: correctly **stereo/multichannel-linked** — a single peak is taken across all channels per frame/sample and the same gain is applied to every channel, preserving the stereo image. Correct design.
- `limiter_processor.c`: delay ring buffer is capped at `NAR_LIMITER_MAX_CHANNELS`; channels beyond that limit get gain applied **without** the look-ahead delay ("minor phase mismatch — acceptable" per the code's own comment). This is honestly documented but is a real, if rare, correctness gap for >N-channel sources (surround/Atmos-style multichannel FLAC) — those extra channels lose sample-accurate alignment with the look-ahead-delayed channels, which could produce audible inter-channel smearing on transients.
- `ebur128_analyzer.cpp` caps at 8 channels (`channels > 8` → nullptr), matching libebur128's own supported channel layouts.

## 7. Sample-Rate Handling (44.1–192 kHz)

- Per memory (`loudness-quality-fixes.md`) sample rate propagation was a previously fixed defect: `loudness_processor.c` used to be hardcoded to 48 kHz. It is now subscribed via `PlaybackManager.audioFormatStream` (`lib/services/audio_service/service.dart:171-178`) which calls `PlaybackManager.setNativeLoudnessSampleRate(sr)` on every track's format. Verified live in code — correctly wired.
- `comp_processor.c` / `limiter_processor.c`: sample rate is passed as an explicit parameter into `nar_comp_set_params()` / `nar_limiter_set_params()` and defaulted to 48000 Hz if `<= 0`. **These are not wired to the same `audioFormatStream` update path** in the excerpts read — they rely on whatever sample rate was in effect at the last explicit `set_params()` call from Settings UI. If the user changes a compressor/limiter setting once at 44.1 kHz and then plays a 192 kHz hi-res file without touching those settings again, the attack/release time constants remain computed for 44.1 kHz. Since `coeff = exp(-1/(ms·0.001·Fs))`, using a stale (lower) Fs makes the *actual* time constant at playback longer than configured (a coefficient computed for 44.1 kHz, when run at 192 kHz's higher per-second sample count, decays more slowly in wall-clock terms) — a real, audible-if-noticed accuracy bug for any user who plays mixed-sample-rate libraries with the compressor/limiter enabled, distinct from and not covered by the "already fixed" loudness sample-rate bug in memory.
- `peq_processor.c` / `crossfeed_processor.c`: coefficients computed from `biquad_filter.c` given an explicit `sample_rate` parameter (clamped to `sample_rate*0.499` Nyquist) — same class of risk as above if not re-triggered on format change, not verified directly this session.
- `NativeDspAudioProcessor.kt` passes the *current* `inputAudioFormat.sampleRate` into every `nativeProcessFloat()` call, so the JNI/C process function always knows the true sample rate per buffer — but only the loudness processor's *state* (envelope/ring-buffer timing) is actually re-derived from that value each track. The others' *stored coefficients* are stale until their own Dart-side `setParams` call re-fires.

## 8. Float Precision

- All DSP math is `float` (32-bit), consistent with Media3's `ENCODING_PCM_FLOAT` pipeline — appropriate precision for real-time audio (no need for `double` given the gain ranges and buffer lengths involved; no long IIR accumulation chains that would benefit from extended precision).
- `gain_processor.c` uses `powf(10, db/20)` (a genuine `pow` call) instead of the faster/more numerically stable `expf(db * ln10/20)` pattern used consistently everywhere else in `dynamics_common.h`. Functionally equivalent, marginally slower, not a precision bug.
- Bit-pattern float↔int32 tricks (`gain_processor.c`, `dynamics_common.h`) are correctly implemented via `memcpy` (not pointer-cast reinterpretation), avoiding strict-aliasing undefined behavior — good practice, no bug.
- `ebur128_analyzer.cpp` correctly uses `double` for LUFS/LU/dB math (appropriate — the offline scan is not real-time-constrained and log-domain accumulation benefits from double precision at this stage).

## 9. Performance (report only — no fixes made)

- Hot-path allocation: zero. `nar_dsp_pipeline_process_raw()` takes a stack-allocated `NarAudioBuffer` view; no heap allocation anywhere in the per-buffer path.
- Transcendental call budget per buffer: gain (1× `powf`), RG (0, precomputed unless dirty), loudness (multiple `logf`/`expf` for K-weighting + gain smoothing, amortized per 100 ms block not per sample), PEQ (0 per sample, precomputed biquad coefficients), compressor (1× `logf` + 1× `expf` per **frame**, not per sample), limiter (0 — pure linear-domain arithmetic), crossfeed (0 per sample, precomputed biquad).
- Compressor's per-frame (not per-sample) `logf`/`expf` is the single largest transcendental cost in the steady-state chain; at 1024-frame buffers / 48 kHz this is ~21 µs of expensive-call budget inside a ~21 ms deadline (per the code's own comment) — negligible margin-wise, but worth knowing it's the most expensive single stage per buffer.
- The dirty-flag double-buffer pattern used everywhere (PEQ, compressor, limiter) means a parameter change is a 20–100 byte `memcpy`, not a transcendental recompute, on the audio thread — correctly designed for zero audio-thread jitter from UI-driven changes.

## 10. Thread Safety — **primary finding of this audit**

Every stateful processor's per-instance mutable fields (`comp_processor.c`'s `envelope_db`; `limiter_processor.c`'s `gain_linear`, `delay_write_pos`, `delay_buf`; `peq_processor.c`'s per-band `s1`/`s2` filter history; `crossfeed_processor.c`'s 4 biquad states; `loudness_processor.c`'s ring buffer and smoothed-gain state) are explicitly commented as **"audio-thread-only state (no atomics needed)"** — an assumption that exactly one audio-rendering thread ever calls `process()` at a time.

That assumption is **violated by the app's own crossfade architecture**. `Media3PlaybackService.kt` owns two concurrently live `ExoPlayer` instances (`primaryPlayer` / `secondaryPlayer`) during every crossfade overlap window (configurable, "up to 30 s" per `AudioOffloadManager.kt`'s own comment). Each `ExoPlayer` instance has its **own** `NativeDspAudioProcessor` Kotlin instance (per the class's own doc comment: "One NativeDspAudioProcessor is created per ExoPlayer instance... All instances call into the same global C pipeline state"), and each ExoPlayer instance renders audio on **its own internal audio-rendering thread**. During the overlap window, both players are actively decoding and rendering audio simultaneously (that is the entire mechanism of an equal-power crossfade — both signals are audible and being mixed by the OS/`AudioTrack` layer at once), so **two distinct native threads can call `nar_dsp_pipeline_process_raw()` concurrently**, both operating on the exact same single global `_comp`, `_lim`, `_peq`, and loudness singleton structs with zero locking and zero atomics protecting the "audio-thread-only" fields.

Concretely, during a crossfade:
- `limiter_processor.c`'s `delay_buf[c][write_pos]` writes and `write_pos`/`gain_linear` read-modify-write from two threads racing on the same 64-slot ring buffer → torn buffer contents (partial writes visible to the other thread), and `gain_linear`/`delay_write_pos` can be corrupted by interleaved non-atomic updates — this is a genuine data race under the C11 memory model (undefined behavior), not just an audible artifact.
- `comp_processor.c`'s `envelope_db` — same class of race; one player's loud passage can instantaneously (and non-deterministically) alter the other player's compression envelope mid-crossfade.
- `peq_processor.c`'s per-band `s1`/`s2` biquad history — same race; interleaved writes from two threads to the same filter-history floats will produce audibly wrong (and technically undefined-behavior) filtering output for whichever samples land in the race window.
- `loudness_processor.c`'s gating ring buffer / smoothed gain — same race class.

Notably, the *hardware offload* layer of this same app is explicitly engineered around exactly this dual-player conflict (`AudioOffloadManager.kt`'s extensive comment block: "DUAL PLAYER — FATAL... two simultaneous ExoPlayer instances... forces the primary off offload mid-song") — the team clearly understood and defended against the dual-player hazard at the OS-offload and system-effects level, but the equivalent hazard inside the **software** native DSP singleton appears to have no analogous defense (no per-player pipeline instance, no mutex around `process()`, no atomic-only state in the stateful processors). `dsp_pipeline.c`'s `process()`/`process_raw()` entry points take no lock at all — only registration/dispose are mutex-guarded.

By contrast, `replaygain_processor.c` and `gain_processor.c` are safe under this scenario: both are fully stateless per-sample (atomic load + scalar multiply, no persistent audio-thread state), so concurrent calls from two players are benign.

**This is the most likely candidate for a genuine, high-impact hidden bug in this codebase.** Expected symptom: an audible click, momentary distortion, brief filter "glitch," or limiter/compressor gain jump specifically during crossfade transitions when any of PEQ, compressor, crossfeed, limiter, or the real-time loudness normalizer are enabled — intermittent and hard to reproduce consistently because it depends on the OS scheduler's actual interleaving of the two players' audio-rendering threads at the moment of the crossfade overlap.

## 11. Runtime Behavior Across Seek / Pause / Resume / Track Change / Crossfade / Gapless

- Seek/flush: `comp_processor.c` (`_comp_reset`), `limiter_processor.c` (`_lim_reset`, clears the delay buffer + resets gain to unity), `peq_processor.c` presumably resets `s1`/`s2` similarly (not directly re-verified this pass but pattern matches). Correctly wired to prevent stale envelope/filter state from leaking across a seek.
- Track change: `AudioService._syncCurrentTrackFromNative()` explicitly resets the loudness analyzer and re-applies RG on every track boundary — correct.
- Crossfade: see §10 — the dual concurrently-active players are the core runtime hazard, not seek/pause/resume individually.
- `onAudioSessionIdChanged` / `onCrossfadeComplete` both call `effectsManager.attachEffects(sessionId)` — this reattaches **system Android `AudioEffect`s** (LoudnessEnhancer, etc.) to the new session ID; it is unrelated to, and does not interact with, the native DSP singleton's own state — the native pipeline has no concept of "session" at all, which is exactly why it doesn't distinguish primary vs. secondary player traffic (reinforcing §10).
- Startup/cold-start: per project memory, `syncFromNative()` uses timeouts around the initial RG apply to avoid a fresh-install hang; not re-verified this pass, no new findings.

## 12. Extreme-Case Mental Testing

- **Silence for the entire track:** loudness processor's absolute gate (−70 LUFS) should hold gain at its floor/neutral value rather than boosting noise-floor hiss toward the target — correctly guarded by the gate logic as read.
- **Extremely loud clipped source (0 dBFS square wave):** RG's clipping-protection cap (`gain × peak ≤ 1.0`) and the limiter's brickwall ceiling both defend against overshoot independently — redundant but not harmful, correct defense in depth, *provided the chain doesn't stop early per §4's stop-on-first-error concern*.
- **Track shorter than the loudness normalizer's smoothing window (e.g. a 1–2 s sound effect):** the 0.3 s attack / 3.0 s release smoothing will barely converge before the track ends — the normalizer will apply close to its initial/neutral gain for most or all of a very short track. Not a bug, but worth knowing: real-time LN is largely ineffective on very short items.
- **Two tracks crossfading where only one has ReplayGain tags:** since RG is resolved and applied per active/standby player independently (based on the track loaded on each), but the *effective gain* is written into the single shared native RG slot, whichever player's Dart-side code last called the RG setter wins for **both** players' audio during the overlap — i.e., the incoming track's gain could momentarily apply to the outgoing track's tail, or vice versa, depending on call ordering. This is the same shared-global-state class of issue as §10, but for a *parameter* race rather than a *state* race — RG's parameter swap is atomic-safe (no torn reads), but the *value* applied during the overlap window is not guaranteed to be correct per-player, because there is only one active gain value for two concurrently playing tracks. Worth flagging as a design-level, not just implementation-level, limitation of a single-instance gain stage feeding two simultaneously audible sources.
- **Rapid enable/disable toggling of Loudness Normalization mid-track (double-tap in Settings):** the Dart-level RG/LN mutual-exclusion check in `_applyReplayGain()` re-evaluates on every toggle, so no obvious inconsistent state was found here; not exhaustively fuzz-tested.

## 13. Android / Media3 / Offload Integration

- `NativeDspAudioProcessor.kt` correctly activates only for `ENCODING_PCM_FLOAT` and fails open (passthrough) if the native library isn't loaded or the pipeline isn't initialized — good defensive design, matches the documented fail-open architecture.
- Hardware audio offload is **deliberately and correctly disabled** in every scenario that would conflict with software DSP/crossfade — the `AudioOffloadManager.kt` is an observer-only class in Media3 1.10.1 (the app cannot force offload scheduling either way anymore since Google removed that API surface; the class's `setForceDisabled()` is now a documented no-op retained only for MethodChannel backward compatibility). This means the app can't actually *prevent* the OS from granting offload on a non-crossfading, effects-free track — if the OS grants it anyway, `NativeDspAudioProcessor` and all system `AudioEffect`s are transparently bypassed by the hardware DSP path per Android's own offload contract, and the audio would play with **no ReplayGain, no loudness normalization, no PEQ/compressor/limiter/clipper at all** while offloaded. This is standard, expected Android/Media3 behavior, not a bug in this codebase — but it is worth the user knowing that hi-res/offload-eligible tracks with no crossfade, no EQ, and no effects enabled could silently play with zero DSP processing whenever offload is OS-granted, since there is no code path here to detect that state and warn/adjust.

## 15. Final Verdict

**Classification: Functionally solid, spec-literate implementation with one genuine, unaddressed concurrency defect.**

The measurement and gain-computation math throughout this pipeline is unusually rigorous for a mobile app — real BS.1770-4 K-weighting coefficients (not an approximation), correct multichannel weighting, a properly designed double-buffered lock-free parameter-update architecture, a genuinely crash-safe tag-writing path with fsync + atomic rename, and an explicitly documented, deliberate RG/LN mutual-exclusion design. The team has clearly reasoned carefully about most edge cases, including ones (hardware offload vs. dual-player) that many teams miss entirely.

The one area where that same rigor was not extended is thread safety across the crossfade boundary: every stateful DSP processor's internal buffers/envelopes assume single-threaded audio access, but the app's own dual-player crossfade design routes two concurrent native audio threads into that same single set of global C structs with zero synchronization. This is a real data race (undefined behavior under C11), not a hypothetical one, and it is specifically the kind of bug that is easy to miss in testing (intermittent, timing-dependent, only manifests when crossfade + PEQ/compressor/limiter/crossfeed/loudness-norm are simultaneously enabled) while being straightforward to demonstrate with a thread sanitizer or by forcibly widening the crossfade overlap window and enabling those effects.

Secondary, lower-severity gaps (missing NaN guards outside the loudness processor, the early-exit-skips-safety-net pipeline behavior, and stale sample-rate-derived time constants for compressor/limiter) are real but narrower in blast radius and lower probability of occurring in normal use.

**Quality score: 7/10.** Deducted primarily for the crossfade-concurrency data race (Finding 1, the dominant factor), with secondary deductions for the missing NaN/Inf defense-in-depth outside the loudness stage and the latent pipeline-abort-on-error behavior. The scanning/tag-writing/measurement math itself would score 9–10/10 in isolation.
