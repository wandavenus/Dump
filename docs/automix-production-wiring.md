# AutoMix production wiring and implementation limits

This document records the production path verified during the follow-up audit for PR #179. It distinguishes live code paths from heuristic metadata and deferred features; a declared enum or unit-tested helper alone is not evidence that a feature affects playback.

## 1. Analysis path and ABI

1. Android `AutomixAnalysisBridge` decodes bounded head / middle / tail PCM windows through `AutomixPcmDownsampler`: a 2-pole Butterworth biquad low-pass runs at the source rate with cutoff $f_c = 0.45 \\times f_{output}$ before decimation. Stereo normally uses an L/R average, but falls back to the stronger channel when the mid signal is below 25% of the stronger channel to avoid near-total phase cancellation. The downsampler also accumulates source-rate center/side power for stereo input, and the bridge passes that global center-channel ratio to `AutomixNative.nativeAnalyzeCentered` for BPM/key/structure/vocal metadata (falling back to `nativeAnalyze` when an older native library lacks the symbol). It calls `nativeAnalyzeChords` for two-second chroma-template chord windows at a one-second hop.
2. JNI (`automix_jni.cpp`) forwards the 28-value result contract from `nar_automix_analyze` in `native_audio_runtime/src/automix_analyzer.c`, including explicit `tailBpmConfidence` (index 20) and the tempo-curve slots: first/last quarter BPM (indices 21/22) and quarter-window stability (index 23), followed by the four per-quarter RMS medians (indices 24-27). `nar_automix_analyze_centered` returns the same 28-value contract with one extra scalar input, the stereo center-channel ratio; the mono entry point passes `NAN`. Stability is the mean octave-folded agreement of the four quarter-window tempo estimates with the whole-window estimate; consumers fold the quarter BPMs into the track BPM's octave at merge time. The quarter RMS profile feeds the intro/outro slope terms used by the planner seam cost.
3. Kotlin maps the output slots to MethodChannel fields. The Dart parser `automixSegmentFeaturesFromAnalysisMap` validates types, finiteness, confidence ranges, key codes and cue offsets rather than silently dropping new fields.
4. `automixMergeSegments` aggregates valid windows and converts window-relative cue positions to file-absolute milliseconds. Vocal likelihood uses confidence-weighted aggregation; tail-only structure, breakdown, and `tailBpmConfidence` metadata are kept distinct from head metadata; the head window supplies `startBpm` and, only when the tail window was actually analyzed, `endBpm` supplies the exit pulse. Adjacent quarter medians become `introSlope` (head window) and `outroSlope` (exit window, tail-only) in dB per quarter.
5. `AutomixService` persists these features using cache schema v15. Older entries are deliberately cache misses so legacy metadata cannot silently replace newly required fields.

The ABI tests enforce the exact 28-value analyzer output, invalid/undersized input behavior, valid confidence ranges, the structure-region enum range, the tempo-curve slot contract, the quarter RMS profile range, and strict silence/noise expectations. Vocal likelihood is a **spectral proxy**, not voice isolation: it now combines the speech-band ratio, centroid stability, cepstral peak prominence, and optional stereo center-channel dominance, and remains confidence-gated with tonal/broadband-noise edge cases tested. The mono/wide confidence cap stays at 0.65; only center-channel evidence unlocks the 0.75 maximum.

## 2. Queue planning

The production planning path is the automatic replan pipeline driven by
playback updates:

`_checkPlaybackStateForAutoMix → _autoAnalyzeUpcomingTracks → AutomixEngine.planSet → NativeAutomix.planSet → nar_automix_plan_set`.

`AutomixService.startAutomix` is a public one-shot entry retained for an explicit
manual start; no UI caller currently invokes it. It shares the same bounded
window (`automixPlanWindow`) and engine call. It is rejected while an automatic
plan pass or another active AutoMix session owns the transition, reports failures
as `-1` instead of throwing, commits its cached tail/signature only after the
playback handoff, and attempts generation-guarded cleanup of the native transition
and crossfade if setup fails. The one-shot caller opts into `playSongAt(rethrowOnError: true)`, which rethrows
handoff failures after restoring Dart state and attempting native queue/playhead/
playback recovery. Existing callers keep the default log-and-return behavior.

The native planner receives 22 feature values per track, plus key and artist-group arrays. Its transition cost currently uses:

- confidence-weighted tempo compatibility and half/double-time variants, measured at the **mix seam**: the outgoing track's exit (tail) tempo when its tail window produced one, otherwise its head estimate, against the incoming track's head tempo;
- estimated key compatibility on the Camelot wheel;
- relative energy shaping across the planned set, plus an intro/outro **section-seam** term (`|outroEnergy_out − introEnergy_in|`) that discourages handing a loud outro into a quiet intro or the reverse when both windows were analyzed;
- an energy **momentum** term from the quarter RMS profile: a still-rising outgoing tail (slope > 1 dB/quarter) that is not matched by an equally building incoming head adds up to 0.30, while a cooling tail stays neutral because the level seam already covers the drop; incomplete or older profiles stay neutral;
- a **structure-shape** term: when both seam windows carry a region label above 0.5 confidence, leaving a peak (drop / stable-high) into a calm or building head, or moving between calm regions, costs nothing, while a peak-to-peak seam costs 0.35 and a drop-to-drop seam 0.5;
- artist repetition avoidance, plus a greedy **artist cooldown**: a candidate whose artist already sits 2–4 positions back is penalized (0.35 with `avoidArtistRepeat`, else 0.15, decaying with distance), including in the one-step lookahead;
- vocal-conflict penalty only when both tracks have useful vocal likelihood and confidence.

The additive seam terms (intro/outro, structure and momentum) stay neutral (zero contribution) when the relevant window was not analyzed or its confidence is below the gate, so they cannot make a partially-analyzed pair worse than the previous whole-track scoring. The Dart reference scorer in `AutomixEngine` mirrors the native cost exactly; parity regressions cover tracks with tail/intro/outro and structure values present.

Ordering is greedy with a bounded one-step lookahead, followed by a multi-pass local improvement pass: pairwise swaps within a bounded breach window, and — for sets of 25+ tracks — Or-opt style single-track relocation and short-segment reversal, each scored over the exact link window they disturb (independent budgets of 4000 swap, 2000 insertion and 1200 reversal evaluations across up to six passes). The relocation/reversal scans are a heuristic: on some fixtures they settle in a different local optimum that can still differ from the swap-only result.

The Dart reference scorer mirrors the native cost. Regression tests exercise high-confidence vocal clashes, a lower-confidence alternative, structural seam preference and confidence gating, artist cooldown spreading, deterministic ordering and native/reference ordering parity (which also exercises the extended polish on 25+ track fixtures).

**Chord progression:** native analysis emits time-stamped root/quality candidates (major, minor, diminished, augmented, dominant 7, major 7, minor 7, suspended 4, suspended 2, half-diminished 7, diminished 7, augmented 7) with a confidence score. Chord and key estimation accumulate a harmonic pitch-class profile (HPCP): spectral peaks in the chroma band are folded onto pitch classes through four harmonics with parabolic log-magnitude peak refinement and a raised-cosine tolerance window of half a semitone, so slightly detuned performances stay on the intended class instead of splitting energy between neighbours. Kotlin and Dart validate the confidence and pitch-class contract; overlapping windows are compressed, results persist in the current cache schema, and confident outgoing-tail/incoming-intro chord clashes can shorten the transition. This is a spectral-template estimator, not a trained transcription model; uncertain or missing chords remain neutral. The vocal estimate is not an ML vocal detector or a source separator, so only confident estimates should influence order.

## 3. Transition decision to Media3 playback

After planning, `AutomixService` computes a cue per incoming track in `automixTransitionCue`. The result includes a strategy code, fade duration, curve, level trims and three-band overlap targets. The strategy selection is confidence-aware:

- `crossfade`: standard fade;
- `structureAligned`: align a fade to a reliable tail breakdown cue;
- `shortHandover`: shorten a confident tempo/key/chord mismatch;
- `longBlend`: extend a sparse-tail/intro blend;
- `quickHandover`: shorten a dense-tail transition.

Early handover scheduling is separate from fade duration. When the incoming track has a
high-confidence drop cue and both tracks have confident beat grids, Dart supplies an
outgoing-track `transitionStartMs`: a reliable breakdown 30–65 seconds from EOF when
available, otherwise an adaptive 35–60 second lead. The lead blends outgoing tail density
(weight 2), a sparse incoming intro (weight 1), and a confident tail structure cue
(region DROP or LOW_ACTIVITY, weight 1); neutral metadata keeps the historical 45 second
lead. Native validates this against the actual media duration, beat-aligns the start, and
keeps the actual fade at its independently planned duration. The standby seeks to the
incoming drop minus the fade duration so the drop lands at the handover; a strong near-end
breakdown or missing/uncertain cue preserves the conventional near-end fade.

`_buildNativeTargets` sends those values through the `musicplayer/automix` MethodChannel. `Media3PlaybackService.applyAutomixTransitionNow` stores them by incoming song ID; `CrossfadeController` retrieves the cue for the standby deck. It validates early-handover cues using the same predicate as the standby drop-seek path and the actual outgoing Media3 duration. Fade progress integrates monotonic wall-clock deltas against the outgoing processor's applied speed on every tick, so it tracks speed changes during the blend and is not coupled to ExoPlayer's default `PlaybackParameters.speed`. The phase-lock sample gate uses an injectable monotonic-time function (production default: `SystemClock.uptimeMillis()`). Controller runnables and completion callbacks are serialized by the main-looper `Handler`; the implementation does not use or claim an `AtomicBoolean` completion guard. If the active player changes underneath a live fade (external takeover), the fade tick takes the abort path, which behaves like a cancel: the deck gains are reset, the takeover deck's volume is restored, the preloaded index is dropped, a promoted one-item timeline is rebuilt, and `onCrossfadeCancelled` is invoked so the service drains any deferred AutoMix target update. The Dart bridge sends only the active/outgoing and immediate incoming target: publishing farther queue entries is unnecessary for the current fade and could let a later repeated song ID overwrite the live pair's ID-keyed settings. If the immediate outgoing and incoming entries share the same song ID, AutoMix-specific targets are omitted for that pair and the conventional crossfade path is retained.

Phrase alignment prefers the offline phrase/downbeat grids. In parallel, the live tracker taps the decoded float PCM in the native audio callback before DSP: a fixed 100 Hz onset envelope, six-second history and periodic autocorrelation update a per-deck BPM / elapsed-beat-phase / downbeat-phase / activity-trend / confidence snapshot. The published phase is selected by scoring each beat-grid phase against the full history (counting onsets within one frame of any grid line) instead of locking onto the single loudest onset, so one irregular accent cannot hijack the estimate. The same history feeds two extra outputs: the four beat positions of a 4/4 bar are scored across the whole window to locate the most recent downbeat (elapsed time since it, plus a margin-based downbeat confidence), and a frame-RMS trend compares the newest quarter of the history window with the quarter before it, so a section build-up reads as a sustained positive value instead of a single level jump. State is isolated for each Media3 stream slot. The audio callback never blocks: it allocates nothing and publishes each estimate through a seqlock using a non-blocking try-lock (under brief control-thread contention that publish is skipped until the next callback), and readers consume a serialized six-field tuple instead of a torn mix of estimates. Live tracking is switched on only while AutoMix has an active transition plan with a non-zero crossfade duration; during a crossfade it is enabled only when the offline planner published valid beat grids for both tracks in that pair. If the planner intentionally omitted a grid for a tempo-mismatched pair, live detection cannot override that decision. For eligible pairs each deck's grid is merged from the analyzer and live tracker instead of choosing one globally: tempos that agree within ~4% blend by weight (live confidence against a fixed analyzer reliability), a tempo mismatch keeps the heavier source whole (a blended half/double reading would match neither), and beat/downbeat phases always follow one clock's source — the live phase wins when the sources agree, the heavier source wins when they disagree, and a rejected live beat source also rejects its downbeat so phrase lock never mixes clock spaces. Confident live downbeats can therefore drive bar-level phrase alignment during a transition even when no offline downbeat grid exists. The current tracker is heuristic and confidence-gated, not a guaranteed beat/downbeat transcription system.

## 4. Feature-driven EQ and overlap headroom

`automixTransitionCue` derives conservative attenuation-only targets from measured RMS-relative energy, onset rate, spectral centroid, structure metadata, and confidence-gated vocal overlap. `CrossfadeController` applies those targets during the overlap; `AutomixToneManager` keeps state per physical player slot; `AutomixToneAudioProcessor` passes controls to the native per-stream tone processor. The native processor smooths atomic target gains and splits bass/mid/high bands without making the audio callback acquire Kotlin locks.

During an AutoMix overlap only, both decks also run a per-stream true-peak limiter in the same native tone stage (`nar_automix_tone_set_true_peak_limit`, ceiling 0.95, disabled with a ceiling of 0). It estimates inter-sample peaks with a 4x cubic Lagrange interpolator over each channel's input history, then applies instant attack and a ~50 ms release before clamping the per-deck sample to the ceiling. The controller enables it for both players when an AutoMix transition starts and disables it on completion, abort, and cancel, so ordinary playback and manual crossfades stay bit-transparent. Because the detector is causal (zero lookahead), the first transient after enabling can briefly over-estimate and over-reduce; the per-sample clamp still keeps the deck output at or below the ceiling. Native tests cover transparency when disabled, ceiling convergence, inter-sample detection, per-stream isolation, reset semantics, and block-boundary continuity. This is still a per-deck limiter, not a shared post-mix bus.

A confident same-mode pair whose folded Camelot distance is 5 is exactly a one-semitone pitch-class difference. For those pairs `automixTransitionCue` publishes `pitchSemitonesOutgoing`; `StretchManager` applies the signed offset only to the outgoing deck for the duration of the overlap and resets it on completion, abort, and cancel. The incoming track keeps its recorded key. Cross-ring pairs (relative major/minor), uncertain keys, and every other wheel distance stay neutral, and the existing key-mismatch strategy is unchanged, so these pairs still use the short handover.

Crossfade gain calculation in `CrossfadeController` delegates to the production `AutomixGainEnvelope` helper. It applies a smooth ramp for `outgoingTrim` (starting at 1.0 at $t=0$ to prevent sudden volume drops), releases `incomingTrim` smoothly to 1.0 at $t=1$, and bounds the **sum of the two deck coefficients** to the current effective target volume on every callback tick. This is an L1 coefficient budget, not an end-to-end post-mix true-peak guarantee. For *uncorrelated* material an L1 bound on the coefficient sum dips the perceived level by up to ~3 dB mid-fade (equal-power, i.e. an L2 bound, would hold it flat); the budget is kept conservative on purpose because the two decks can be phase-correlated and the sum is mixed downstream by AudioFlinger with no shared post-mix limiter (see below). The per-transition curve value (`curveGamma`, clamped to $[0.6, 1.6]$) is applied as $t^{1/\\gamma}$: values above 1 accelerate the handover (incoming rises faster), values below 1 stretch the blend. The JVM envelope and the native C helper share this definition, and a directional regression pins incoming/outgoing gains at $t = 0.25/0.5/0.75$ for $\\gamma$ above and below 1. JVM tests call this same production helper across progress, trim, curve and target-volume combinations; they are not a substitute for device-level PCM capture or listening tests. The scalar C path and ARM64 NEON path also clamp each stream's processed PCM sample to $[-1, 1]$. Native tests cover per-stream over-range sample clamping.

**Safety limit and dual-stream architecture:**
Two independent ExoPlayer instances process and output audio streams through separate AudioTracks, which Android AudioFlinger mixes downstream.
- **Headroom scaling:** Per-stream equal-power gain scaling ($G_{out}^2 + G_{in}^2 \le 1.0$) prevents overload for uncorrelated sources at the fader stage.
- **Per-stream sample clamp:** The native DSP pipeline clamps each stream's PCM samples to $[-1.0, 1.0]$.
- **Per-deck true-peak limiting:** During an AutoMix overlap the tone stage bounds each deck's interpolated true peak (causal 4x Lagrange, instant attack, ~50 ms release, ceiling 0.95). Combined with the L1 coefficient budget this bounds the phase-aligned mix at roughly the ceiling, but it is not a post-mix guarantee.
- **Post-mix limitations:** Per-stream limiting does not guarantee that the downstream mixed sum of two correlated signals or signals with constructive phase alignment remains below $0\text{ dBFS}$, because the two decks are summed after both limiters. A correlated peak in one deck can coincide with a peak in the other, and the sources' inter-sample peaks are not aligned in time.
- **Shared software mix bus assessment:** Genuinely guaranteeing post-mix true-peak limits would require a single shared software mix bus with an oversampled true-peak limiter receiving PCM from both decoders prior to output.
No post-mix true-peak protection claim is made for the current dual-AudioTrack implementation; the verified guarantees are per-stream sample clamping, per-deck true-peak limiting during an AutoMix overlap, and fader coefficient headroom bounds.

## 5. Reproducible SDK setup and validation

`setup-flutter.sh` resolves the official stable release manifest before deciding whether to reuse the workspace SDK. Reuse requires the version and a release stamp matching the official release hash and archive checksum; a new archive is SHA-256 checked against the manifest before extraction. Legacy un-stamped SDK copies are refreshed instead of trusted based on their self-reported version alone.

The PR verification workflow syntax-checks `setup-flutter.sh` and dispatches the Flutter analyzer/full test suite, focused AutoMix Dart/cache tests, native C/DSP tests with ASan/UBSan, Kotlin unit tests, and an Android ARM64 debug build. The native workflow additionally compiles the in-repo AutoMix C suite (`native_audio_runtime/test/automix_native_c_test.c` linked against the `automix_*` sources) directly: an x86_64 build runs under ASan/UBSan, and an `aarch64-linux-gnu-gcc` build executes under `qemu-aarch64-static` so the NEON window/RMS and stereo-tone assembly paths are actually run rather than only cross-checked. Test status is evidence only for the exact source SHA recorded in each run; the dispatch job succeeding means the linked jobs started, not that all of them passed.

## 6. Explicitly deferred functionality

- **True-peak limiting:** not implemented. The validated guarantee is a per-stream sample-peak clamp and bounded overlap gain budget only.

Live beat tracking and confidence-gated chord progression analysis now have production paths described above. The live tracker remains heuristic; the chord classifier is a bounded spectral-template estimator. Neither claims model-level transcription accuracy.
