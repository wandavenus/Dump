# AutoMix production wiring and implementation limits

This document records the production path verified during the follow-up audit for PR #179. It distinguishes live code paths from heuristic metadata and deferred features; a declared enum or unit-tested helper alone is not evidence that a feature affects playback.

## 1. Analysis path and ABI

1. Android `AutomixAnalysisBridge` decodes bounded head / middle / tail PCM windows through `AutomixPcmDownsampler`: a 2-pole Butterworth biquad low-pass runs at the source rate with cutoff $f_c = 0.45 \\times f_{output}$ before decimation. Stereo normally uses an L/R average, but falls back to the stronger channel when the mid signal is below 25% of the stronger channel to avoid near-total phase cancellation. The downsampler also accumulates source-rate center/side power for stereo input, and the bridge passes that global center-channel ratio to `AutomixNative.nativeAnalyzeCentered` for BPM/key/structure/vocal metadata (falling back to `nativeAnalyze` when an older native library lacks the symbol). For multichannel sources an Android channel mask identifies and excludes the LFE channel from the temporally weighted downmix. It calls `nativeAnalyzeChords` for two-second chroma-template chord windows at a one-second hop.
2. JNI (`automix_jni.cpp`) forwards the 32-value result contract from `nar_automix_analyze` in `native_audio_runtime/src/automix_analyzer.c`, including explicit `tailBpmConfidence` (index 20), first/last quarter BPM (indices 21/22), tempo stability (index 23), four per-quarter RMS medians (indices 24-27), local-quarter BPM confidence (indices 28/29), and beat phases measured with those local BPMs (indices 30/31). The local phase slots are folded to their quarter's beat period so they cannot be accidentally paired with the whole-window tempo. `nar_automix_analyze_centered` returns the same 32-value contract with one extra scalar input, the stereo center-channel ratio; the mono entry point passes `NAN`. Stability is the mean octave-folded agreement of the four quarter-window tempo estimates with the whole-window estimate; consumers fold the quarter BPMs into the track BPM's octave at merge time. The quarter RMS profile feeds the intro/outro slope terms used by the planner seam cost.
3. Kotlin maps the output slots to MethodChannel fields. The Dart parser `automixSegmentFeaturesFromAnalysisMap` validates types, finiteness, confidence ranges, key codes and cue offsets rather than silently dropping new fields.
4. `automixMergeSegments` aggregates valid windows and converts window-relative cue positions to file-absolute milliseconds. Vocal likelihood uses confidence-weighted aggregation; tail-only structure, breakdown, and `tailBpmConfidence` metadata are kept distinct from head metadata. The exit pulse only reads the final (tail) window. It prefers `endBpm` when its own local-quarter confidence is at least 0.35 and keeps the matching `endBeatOffsetMs`; otherwise the whole-window tail BPM and phase remain the fallback. If that tail window has no usable tempo, the exit grid stays unknown instead of borrowing a middle/head window's tempo or phase. A tail window counts as analyzed only after the decoder reports actual End-Of-Stream; a full capped buffer without that proof remains partial and retryable. Incoming-edge scoring similarly prefers a confident `startBpm`. Measured edge stability weights tempo costs and gates playback tempo pull at 0.65; unstable pairs retain a conventional crossfade instead of forcing varispeed. Adjacent quarter medians become `introSlope` (head window) and `outroSlope` (exit window, tail-only) in dB per quarter.
5. `AutomixService` persists these features using cache schema v16. Older entries are deliberately cache misses so legacy metadata cannot silently replace newly required fields.

The ABI tests enforce the exact 32-value analyzer output, invalid/undersized input behavior, valid confidence ranges, the structure-region enum range, the tempo-curve slot contract, the quarter RMS profile range, and strict silence/noise expectations. Vocal likelihood is a **spectral proxy**, not voice isolation: it now combines the speech-band ratio, centroid stability, cepstral peak prominence, and optional stereo center-channel dominance, and remains confidence-gated with tonal/broadband-noise edge cases tested. The mono/wide confidence cap stays at 0.65; only center-channel evidence unlocks the 0.75 maximum.

## 2. Queue planning

The production planning path is the automatic replan pipeline driven by
playback updates:

`_checkPlaybackStateForAutoMix → _autoAnalyzeUpcomingTracks → AutomixEngine.planSet → NativeAutomix.planSet → nar_automix_plan_set`.

`AutomixService.startAutomix` is a public one-shot entry retained for an explicit
manual start; no UI caller currently invokes it. It shares the same bounded
window (`automixPlanWindow`) and engine call. It is rejected while an automatic
plan pass or another active AutoMix session owns the transition, reports failures
as `-1` instead of throwing, commits its cached tail/signature only after the
playback handoff, and attempts generation-guarded cleanup of the native transition
and crossfade if setup fails. The one-shot caller opts into `playSongAt(rethrowOnError: true)`, which rethrows
handoff failures after restoring Dart state and attempting native queue/playhead/
playback recovery. Existing callers keep the default log-and-return behavior.

The native planner receives 27 feature values per track (`NAR_AUTOMIX_FEATURE_COUNT`), plus key and artist-group arrays. Tail BPM and tail BPM confidence occupy separate feature slots. A confident exit tempo (`endBpm` at ≥0.35 local confidence) takes precedence; otherwise the merge may publish the tail window's whole-window BPM. If the tail window has no usable tempo at all, `tailBpm`/`tailBpmConfidence`/tail phase stay unset, and the planner falls back to the head tempo for sequencing only. Its transition cost currently uses:

- confidence-weighted tempo compatibility and half/double-time variants, measured at the **mix seam**: the outgoing track's exit tempo when the tail BPM confidence is at least 0.35, otherwise its head estimate; the confidence paired with that tempo is always from the same analysis window;
- estimated key compatibility on the Camelot wheel;
- relative energy shaping across the planned set, plus an intro/outro **section-seam** term (`|outroEnergy_out − introEnergy_in|`) that discourages handing a loud outro into a quiet intro or the reverse when both windows were analyzed;
- an energy **momentum** term from the quarter RMS profile: a still-rising outgoing tail (slope > 1 dB/quarter) that is not matched by an equally building incoming head adds up to 0.30, while a cooling tail stays neutral because the level seam already covers the drop; incomplete or older profiles stay neutral;
- a **structure-shape** term: when both seam windows carry a region label above 0.5 confidence, leaving a peak (drop / stable-high) into a calm or building head, or moving between calm regions, costs nothing, while a peak-to-peak seam costs 0.35 and a drop-to-drop seam 0.5;
- artist repetition avoidance, plus a greedy **artist cooldown**: a candidate whose artist already sits 2–4 positions back is penalized (0.35 with `avoidArtistRepeat`, else 0.15, decaying with distance), including in the one-step lookahead;
- vocal-conflict penalty only when both tracks have useful vocal likelihood and confidence.

The additive seam terms (intro/outro, structure and momentum) stay neutral (zero contribution) when the relevant window was not analyzed or its confidence is below the gate, so they cannot make a partially-analyzed pair worse than the previous whole-track scoring. The Dart reference scorer in `AutomixEngine` mirrors the native cost exactly; parity regressions cover tracks with tail/intro/outro and structure values present.

Ordering is greedy with a bounded one-step lookahead, followed by a multi-pass local improvement pass: pairwise swaps within a bounded breach window, and — for sets of 25+ tracks — Or-opt style single-track relocation and short-segment reversal, each scored over the exact link window they disturb (independent budgets of 4000 swap, 2000 insertion and 1200 reversal evaluations across up to six passes). The relocation/reversal scans are a heuristic: on some fixtures they settle in a different local optimum that can still differ from the swap-only result.

The Dart reference scorer mirrors the native cost. Regression tests exercise high-confidence vocal clashes, a lower-confidence alternative, structural seam preference and confidence gating, artist cooldown spreading, deterministic ordering and native/reference ordering parity (which also exercises the extended polish on 25+ track fixtures).

**Chord progression:** native analysis emits time-stamped root/quality candidates (major, minor, diminished, augmented, dominant 7, major 7, minor 7, suspended 4, suspended 2, half-diminished 7, diminished 7, augmented 7) with a confidence score. Chord and key estimation accumulate a harmonic pitch-class profile (HPCP): spectral peaks in the chroma band are folded onto pitch classes through four harmonics with parabolic log-magnitude peak refinement and a raised-cosine tolerance window of half a semitone, so slightly detuned performances stay on the intended class instead of splitting energy between neighbours. Kotlin and Dart validate the confidence and pitch-class contract; overlapping windows are compressed, results persist in the current cache schema, and confident outgoing-tail/incoming-intro chord clashes can shorten the transition. This is a spectral-template estimator, not a trained transcription model; uncertain or missing chords remain neutral. The vocal estimate is not an ML vocal detector or a source separator, so only confident estimates should influence order.

## 3. Transition decision to Media3 playback

After planning, `AutomixService` computes a cue per incoming track in `automixTransitionCue`. The result includes a strategy code, fade duration, curve, level trims and three-band overlap targets. The strategy selection is confidence-aware:

- `crossfade`: standard fade;
- `structureAligned`: align a fade to a reliable tail breakdown cue;
- `shortHandover`: shorten a confident tempo/key/chord mismatch;
- `longBlend`: extend a sparse-tail/intro blend;
- `quickHandover`: shorten a dense-tail transition.

Early handover scheduling is separate from fade duration. When the incoming track has a
high-confidence drop cue and both tracks have confident beat grids, Dart supplies an
outgoing-track `transitionStartMs`: a reliable breakdown 30–65 seconds from EOF when
available, otherwise an adaptive 35–60 second lead. The lead blends outgoing tail density
(weight 2), a sparse incoming intro (weight 1), and a confident tail structure cue
(region DROP or LOW_ACTIVITY, weight 1); neutral metadata keeps the historical 45 second
lead. Native validates this against the actual media duration, beat-aligns the start, and
keeps the actual fade at its independently planned duration. The standby seeks to the
incoming drop minus the fade duration so the drop lands at the handover; a strong near-end
breakdown or missing/uncertain cue preserves the conventional near-end fade.

`_buildNativeTargets` sends those values through the `musicplayer/automix` MethodChannel. `Media3PlaybackService.applyAutomixTransitionNow` stores them by incoming song ID; `CrossfadeController` retrieves the cue for the standby deck. It validates early-handover cues using the same predicate as the standby drop-seek path and the actual outgoing Media3 duration. Fade progress integrates monotonic wall-clock deltas against the outgoing processor's applied speed on every tick, so it tracks speed changes during the blend and is not coupled to ExoPlayer's default `PlaybackParameters.speed`. The phase-lock sample gate uses an injectable monotonic-time function (production default: `SystemClock.uptimeMillis()`). Controller runnables and completion callbacks are serialized by the main-looper `Handler`; the implementation does not use or claim an `AtomicBoolean` completion guard. If the active player changes underneath a live fade (external takeover), the fade tick takes the abort path, which behaves like a cancel: the deck gains are reset, both deck volumes are restored (including the partially faded-in promoted deck), both decks that no longer own playback are paused/stopped and have their media items cleared, the preloaded index is dropped, a promoted one-item timeline is rebuilt, and `onCrossfadeCancelled` is invoked so the service drains any deferred AutoMix target update. The Dart bridge sends only the active/outgoing and immediate incoming target: publishing farther queue entries is unnecessary for the current fade and could let a later repeated song ID overwrite the live pair's ID-keyed settings. If the immediate outgoing and incoming entries share the same song ID, AutoMix-specific targets are omitted for that pair and the conventional crossfade path is retained.

A duration update is not a transition reset. While `crossfadeInProgress` is true, a positive `setCrossfadeDuration` only updates the duration used by the next transition and refreshes offload eligibility; it must not call `cancel`, clear the standby queue, or restore the promoted queue. A duration of zero keeps the cancel path because it disables crossfade and a live blend must stop. Dart additionally avoids re-sending an unchanged duration during a replan, but the native guard is authoritative because `AudioEffectsService.applyAll()` and the settings UI can reach the same MethodChannel independently. During promotion, the session switch uses `copyVolume = false` and the controller re-asserts `standby.volume = 0f` after the switch, so the incoming deck stays muted until the first equal-power tick even when the outgoing deck was near full volume.

Phrase alignment prefers the offline phrase/downbeat grids. In parallel, the live tracker taps the decoded float PCM in the native audio callback before DSP: a fixed 100 Hz onset envelope, six-second history and periodic autocorrelation update a per-deck BPM / elapsed-beat-phase / downbeat-phase / activity-trend / confidence snapshot. The published phase is selected by scoring each beat-grid phase against the full history (counting onsets within one frame of any grid line) instead of locking onto the single loudest onset, so one irregular accent cannot hijack the estimate. The same history feeds two extra outputs: the four beat positions of a 4/4 bar are scored across the whole window to locate the most recent downbeat (elapsed time since it, plus a margin-based downbeat confidence), and a frame-RMS trend compares the newest quarter of the history window with the quarter before it, so a section build-up reads as a sustained positive value instead of a single level jump. State is isolated for each Media3 stream slot. The audio callback never blocks: it allocates nothing and publishes each estimate through a seqlock using a non-blocking try-lock (under brief control-thread contention that publish is skipped until the next callback), and readers consume a serialized six-field tuple instead of a torn mix of estimates. Live tracking is switched on whenever the native AutoMix transition is active (with two distinct target IDs) and the crossfade duration is non-zero. The offline beat-grid gate applies to phase lock, not to tracker collection: `CrossfadeController` only enables phase lock when the published offline targets say the pair passed tempo matching, so live detection cannot override a deliberately unmatched pair even though the tracker keeps measuring. For eligible pairs each deck's grid is merged from the analyzer and live tracker instead of choosing one globally: tempos that agree within ~4% blend by weight (live confidence against a fixed analyzer reliability), a tempo mismatch keeps the heavier source whole (a blended half/double reading would match neither), and beat/downbeat phases always follow one clock's source — the live phase wins when the sources agree, the heavier source wins when they disagree, and a rejected live beat source also rejects its downbeat so phrase lock never mixes clock spaces. Confident live downbeats can therefore drive bar-level phrase alignment during a transition even when no offline downbeat grid exists. The current tracker is heuristic and confidence-gated, not a guaranteed beat/downbeat transcription system.

## 4. Feature-driven EQ and overlap headroom

`automixTransitionCue` derives conservative attenuation-only targets from measured RMS-relative energy, onset rate, spectral centroid, structure metadata, and confidence-gated vocal overlap. `CrossfadeController` applies those targets during the overlap; `AutomixToneManager` keeps state per physical player slot; `AutomixToneAudioProcessor` passes controls to the native per-stream tone processor. The native processor smooths atomic target gains and splits bass/mid/high bands without making the audio callback acquire Kotlin locks.

During an AutoMix overlap only, both decks also run a per-stream true-peak limiter in the native tone stage (`nar_automix_tone_set_true_peak_limit`, ceiling 0.95, disabled with a ceiling of 0). The production chain places that tone stage after `SignalsmithStretchAudioProcessor`, so the limiter sees the stretched/pitch-shifted signal and its ceiling also covers inter-sample peaks introduced by the stretch stage. It estimates inter-sample peaks with a 4x cubic Lagrange interpolator over each channel's input history, then applies instant attack and a ~50 ms release before clamping the per-deck sample to the ceiling. The controller enables it for both players when an AutoMix transition starts. On completion, abort, and cancel it targets a ceiling of 0, and the native stage ramps the effective ceiling back to 1.0 while the release gain settles; only then does it drop to the transparent path. This removes the end-of-overlap clamp step instead of disabling the limiter in place, so ordinary playback and manual crossfades remain bit-transparent without a click. Because the detector is causal (zero lookahead), it cannot see a peak that lies between the current and next input samples until the next frame, so that boundary can briefly remain above the interpolated ceiling; the zero-initialized history can also over-reduce the first few frames. The per-sample clamp still keeps the deck's sample peak at or below the ceiling, but this is an estimator/limiter, not a lookahead true-peak guarantee. Native tests cover transparency when disabled, ceiling convergence, smooth disable at a block boundary, inter-sample detection, per-stream isolation, reset semantics, and block-boundary continuity. `player.volume` is applied after the chain and only attenuates further. This is still a per-deck limiter, not a shared post-mix bus.

A confident same-mode pair whose folded Camelot distance is 5 is exactly a one-semitone pitch-class difference. For those pairs `automixTransitionCue` publishes `pitchSemitonesOutgoing`; `StretchManager` applies the signed offset only to the outgoing deck for the duration of the overlap and resets it on completion, abort, and cancel. Once the STFT engine has produced audio, the processor stays on the STFT path until a flush/reset instead of switching to raw bypass when the smoothed rate reaches exactly 1.0; the latency-bearing STFT tail can therefore finish without a hard splice at the end of the tempo match. The incoming track keeps its recorded key. Cross-ring pairs (relative major/minor), uncertain keys, and every other wheel distance stay neutral, and the existing key-mismatch strategy is unchanged, so these pairs still use the short handover.

Crossfade gain calculation in `CrossfadeController` delegates to the production `AutomixGainEnvelope` helper. It applies a smooth ramp for `outgoingTrim` (starting at 1.0 at $t=0$ to prevent sudden volume drops), releases `incomingTrim` smoothly to 1.0 at $t=1$, and bounds the **sum of the two deck coefficients** to the current effective target volume on every callback tick. This is an L1 coefficient budget, not an end-to-end post-mix true-peak guarantee. For *uncorrelated* material an L1 bound on the coefficient sum dips the perceived level by up to ~3 dB mid-fade (equal-power, i.e. an L2 bound, would hold it flat); the budget is kept conservative on purpose because the two decks can be phase-correlated and the sum is mixed downstream by AudioFlinger with no shared post-mix limiter (see below). The per-transition curve value (`curveGamma`, clamped to $[0.6, 1.6]$) is applied as $t^{1/\\gamma}$: values above 1 accelerate the handover (incoming rises faster), values below 1 stretch the blend. The JVM envelope and the native C helper share this definition, and a directional regression pins incoming/outgoing gains at $t = 0.25/0.5/0.75$ for $\\gamma$ above and below 1. JVM tests call this same production helper across progress, trim, curve and target-volume combinations; they are not a substitute for device-level PCM capture or listening tests. The scalar C path and ARM64 NEON path also clamp each stream's processed PCM sample to $[-1, 1]$. Native tests cover per-stream over-range sample clamping.

**Safety limit and dual-stream architecture:**
Two independent ExoPlayer instances process and output audio streams through separate AudioTracks, which Android AudioFlinger mixes downstream.
- **Headroom scaling:** Per-stream equal-power gain scaling ($G_{out}^2 + G_{in}^2 \le 1.0$) prevents overload for uncorrelated sources at the fader stage.
- **Per-stream sample clamp:** The native DSP pipeline clamps each stream's PCM samples to $[-1.0, 1.0]$.
- **Per-deck true-peak estimation/limiting:** During an AutoMix overlap the post-Stretch tone stage estimates each deck's interpolated peak (causal 4x Lagrange, instant attack, ~50 ms release, ceiling 0.95) and clamps its samples. Because there is no lookahead, a future-sample transient can still leave a brief inter-sample overshoot. Combined with the L1 coefficient budget this keeps the phase-aligned mix near the ceiling, but it is not a post-mix true-peak guarantee.
- **Post-mix limitations:** Per-stream limiting does not guarantee that the downstream mixed sum of two correlated signals or signals with constructive phase alignment remains below $0\text{ dBFS}$, because the two decks are summed after both limiters. A correlated peak in one deck can coincide with a peak in the other, and the sources' inter-sample peaks are not aligned in time.
- **Shared software mix bus assessment:** Genuinely guaranteeing post-mix true-peak limits would require a single shared software mix bus with an oversampled true-peak limiter receiving PCM from both decoders prior to output.
No post-mix true-peak protection claim is made for the current dual-AudioTrack implementation; the verified guarantees are per-stream sample clamping, causal per-deck inter-sample peak estimation/attenuation during an AutoMix overlap, and fader coefficient headroom bounds.

## 5. Reproducible SDK setup and validation

`setup-flutter.sh` resolves the official stable release manifest before deciding whether to reuse the workspace SDK. Reuse requires the version and a release stamp matching the official release hash and archive checksum; a new archive is SHA-256 checked against the manifest before extraction. Legacy un-stamped SDK copies are refreshed instead of trusted based on their self-reported version alone.

For same-repository PRs the verification workflow syntax-checks `setup-flutter.sh` and dispatches the Flutter analyzer/full test suite, focused AutoMix Dart/cache tests, native C/DSP tests with ASan/UBSan, Kotlin unit tests, and an Android ARM64 debug build. Fork PRs skip that secret-backed job but still run the local Android ARM64 build validation. The native workflow additionally compiles the in-repo AutoMix C suite (`native_audio_runtime/test/automix_native_c_test.c` linked against the `automix_*` sources) directly: an x86_64 build runs under ASan/UBSan, and an `aarch64-linux-gnu-gcc` build executes under `qemu-aarch64-static` so the NEON window/RMS and stereo-tone assembly paths are actually run rather than only cross-checked. Test status is evidence only for the exact source SHA recorded in each run; the dispatch job succeeding means the linked jobs started, not that all of them passed.

`tools/automix_ffmpeg_regression.sh` adds an offline audio check that is independent of device playback. FFmpeg generates deterministic 48 kHz float source signals, the JVM test renders the production Kotlin `AutomixGainEnvelope` fallback at the 16 ms tick cadence, and FFmpeg `astats` measures peak level and maximum sample-to-sample difference on the result. The same harness renders two legacy fault models (mid-fade cancel and pre-fade volume copy) to prove the metric catches those regressions. The current envelope must stay below 0.05 max sample step and 0 dBFS peak; the legacy models must exceed 0.25/0.20 respectively. This validates sample continuity and gain headroom for the Kotlin envelope only; it does not exercise the native C/NEON per-deck envelope, ExoPlayer scheduling, AudioTrack buffering, or the device mixer.

## 6. Explicitly deferred functionality

- **Post-mix true-peak limiting:** not implemented. Causal per-deck inter-sample peak estimation/attenuation runs after Stretch (ceiling 0.95) and the overlap gain budget is L1-bounded, but the two decks are summed downstream by AudioFlinger with no shared post-mix limiter. The validated guarantee therefore remains per-deck sample-level plus causal inter-sample attenuation, not end-to-end true peak.

Live beat tracking and confidence-gated chord progression analysis now have production paths described above. The live tracker remains heuristic; the chord classifier is a bounded spectral-template estimator. Neither claims model-level transcription accuracy.
